# ADR-0001: 本地优先 + CRDT 多端同步架构

## 状态
**已接受**

## 日期
2026-07-26

## 背景
当前项目是一个基于 Vue 3 + Electron 的桌面端待办应用，数据存储在本地 `db.json` 文件中（开发模式使用 json-server，生产模式使用 Electron IPC + fs 读写）。需要扩展到支持 macOS（已有）、iOS、Android 三端，且实现跨设备数据互通。

核心约束：
- **无中心化服务器** — 用户不希望运维一个中心服务器
- **用户管理自己的数据** — 数据主权归用户
- **多端互通** — macOS / iOS / Android 之间数据一致
- **离线可用** — 无网络时也能正常使用

## 决策

### 1. 数据层：采用 CRDT（无冲突复制数据类型）

选用 **Automerge**（版本 2.x）作为核心数据模型。

#### 理由
| 方案 | 优点 | 缺点 |
|------|------|------|
| **CRDT (Automerge)** ✅ | 无冲突合并、离线优先、无需中心服务器 | 学习曲线、文档体积稍大 |
| SQLite + 云文件同步 | 成熟、性能好 | 并发写入导致文件损坏风险高 |
| PouchDB + CouchDB | 成熟的双向同步 | 需要 CouchDB 服务器 |
| 自建 REST API 服务器 | 简单直接 | ❌ 需要中心化服务器 |

CRDT 的核心优势：
- 多个设备可以同时离线编辑
- 联网后自动合并，无需处理冲突
- 数据存储为 Append-Only Log，天然支持历史回溯

### 2. 跨平台方案：Electron (Desktop) + Capacitor (Mobile)

| 平台 | 技术 |
|------|------|
| **macOS Desktop** | Electron（已有，保留） |
| **iOS** | Capacitor（复用 Vue 3 代码） |
| **Android** | Capacitor（复用 Vue 3 代码） |

Capacitor 相对 React Native / Flutter 的优势：
- 可 **100% 复用现有 Vue 3 + TypeScript + Pinia + Tailwind 代码**
- 提供原生插件访问文件系统、云存储 API
- 社区成熟、维护活跃
- 轻量级（相对 Electron）

### 3. 同步机制：用户自选云存储 + CRDT 文件同步

用户数据存储在用户自己选择的云存储中：

| 平台 | 推荐云存储 |
|------|-----------|
| macOS Desktop | iCloud Drive / 本地文件夹（用户可将其放入任意云盘） |
| iOS | iCloud Drive |
| Android | Google Drive |

**同步流程**：
1. CRDT 文档序列化为单个 JSON 文件（如 `todos.automerge`）
2. 文件保存在用户云存储目录中
3. 本地维护一份缓存副本（IndexedDB / LocalStorage / fs）
4. 启动时：读取云文件 → 与本地合并 → 渲染 UI
5. 变更时：写本地 → 写云文件
6. 云文件变化时（另一设备写入）：自动检测并合并

### 4. 存储路径策略

```
用户云盘/
  └── TodoApp/
      └── data.automerge    # CRDT 文档文件（核心数据）
      └── settings.json     # 用户设置（非同步或选择性同步）
```

### 5. 离线优先原则

- 所有读写操作先针对本地缓存
- 云文件写入在后台异步进行
- 无网络时完整体验不受影响
- 联网后自动合并来自其他设备的变更

## 后果

### 正面
- ✅ 用户完全拥有自己的数据
- ✅ 无需运维任何服务器
- ✅ 离线功能完整
- ✅ 多端自动合并，无冲突烦恼
- ✅ 可以复用现有全部 Vue 3 代码

### 负面
- ⚠️ 需要引入 Automerge 库（新增依赖）
- ⚠️ 需要重构数据访问层（从 REST/IPC → CRDT）
- ⚠️ 云存储 API 集成需要各平台原生能力
- ⚠️ CRDT 文档随数据量增长可能变大（需定期 GC）

### 缓解措施
- Automerge 2.x 已大幅优化性能，百万级文档仍可流畅操作
- 对于纯文本 todo 数据（非大文件附件），文档体积增长可控
- 可定期运行 CRDT 压缩（Automerge 内置支持）

## 备选方案

### 备选 A：SQLite + 云文件
- 问题：SQLite 是单一二进制文件，两个设备同时写入会导致文件损坏
- 需要复杂的文件锁机制，在云存储场景下不可靠

### 备选 B：自建 WebSocket 服务器
- 问题：需要中心化服务器，违背用户意愿
- 优势：实时性更好
- 结论：不适合本场景

### 备选 C：P2P 直连 (WebRTC)
- 问题：需要信令服务器，设备不在同一网络时连接困难
- 优势：完全去中心化
- 结论：实现复杂，用户门槛高

## 结论
采用 **CRDT (Automerge) + Electron/Capacitor + 用户自选云存储** 的架构，在数据主权、离线体验、开发效率之间取得最佳平衡。
